# Continuum device and controller management

Continuum reads a versioned device registry from `NMC_DEVICE_INVENTORY_PATH` (the Ansible deployment seeds an empty version-1 document at `/var/lib/nmc/device-inventory.json` when no registry exists). The registry is an operator-generated export of verified inventory and dependency data; Continuum does not scan arbitrary address ranges. Populate it from the authoritative network registry and discovery results so discovered devices can be reconciled without silently replacing verified identities. Keep the registry under `/var/lib/nmc`, outside temporary/runtime directories, and preserve it across service restarts, host reboots and package upgrades; deployment seeds it only when absent, and the release playbook checks its checksum around package installation. Keep the file a single-link regular file, owned by the service account and not writable by group or other users; the server opens it without following a symbolic link. The empty seed makes the API schema available but does not mean that any host, dependency, BMC or DHCP source has been discovered or verified.

The JSON document uses `schema_version: 1`, an inventory `revision`, a `dependency_graph_revision`, `generated_at_unix_ms`, `max_age_ms`, `devices`, and `controllers`. Each device has a stable `id`, `kind`, explicit `depends_on` array, hosted `services`, and the complete `affected_services` set used when checking the impact of a restart. A controller declares `id`, `protocol` (`redfish`, `ipmi`, or `turingpi`), `endpoint`, `manages`, and `power_actions_enabled`; when known from a verified network registry, its six-octet `mac_address` is also recorded and exposed by the read-only inventory API. A controller's MAC is identity evidence, not an authorisation token. Redfish controllers may also declare `vendor_profile`: `generic_redfish`, `hp_ilo`, `dell_idrac`, or `ami_megarac`. This field describes the expected vendor family; all three vendor profiles use standard Redfish resource discovery and advertised capabilities without assuming proprietary endpoints or actions. The controller's `manages` list and every managed device's `controller_id` must agree. Redfish devices also set `controller_target` to the Redfish ComputerSystem `Id`; actions resolve that ID through the service root's advertised Systems collection instead of constructing a vendor-specific path. Turing Pi devices set `turingpi_slot` from 1 through 4. Unknown IDs, duplicate identifiers, stale inventory, malformed mappings, and unsupported protocols fail closed.

Use `username_env` and `password_env` to refer to credentials provided through the server process environment. Secret values never belong in the registry or API responses. Redfish and Turing Pi endpoints must use HTTPS with certificate verification enabled. Use `tls_ca_file` for a private CA bundle; Continuum does not disable verification for self-signed BMC certificates. IPMI runs `ipmitool` directly without a shell and supplies its password through the child process environment (`IPMI_PASSWORD`/`-E`), never through argv. Install `ipmitool` on the Continuum server when IPMI controllers are configured.

Home Assistant is supplemental. `home_assistant` accepts `base_url`, `token_env`, an explicit `entities` allowlist, and optional `tls_ca_file`. Plain HTTP is accepted only when `allow_http: true` and the endpoint uses a loopback or private IP address literal; private hostnames must use HTTPS to avoid DNS rebinding to public addresses. The state API returns only allowlisted entity IDs, states and update timestamps; it never returns Home Assistant attributes or unrelated person/presence entities. The reconciliation API compares each registered `home_assistant_entity` to that same allowlist and current state snapshot by exact entity ID. It reports `matched`, `missing`, `not_configured`, and `ambiguous` mappings, plus explicitly allowlisted but unregistered entity IDs. State values are included only for one-to-one matches; ambiguous and unmapped entries never inherit a device's identity. The report is read-only, carries its inventory revision and freshness, and does not automatically add devices, rewrite the registry, or authorize hardware actions.

DHCP sources are explicit verified collectors in the inventory's optional `dhcp_servers` array. Each entry has a stable `id`, expected `server_id`, HTTPS `endpoint`, and `token_env`; private-address HTTP requires `allow_http: true`, and private certificate authorities may use `tls_ca_file`. Plain HTTP endpoints must use a loopback or private IP address literal. Continuum performs only authenticated `GET <endpoint>/api/v1/dhcp/leases` requests, with redirects disabled, bounded timeouts and at most eight configured sources queried concurrently. It does not broadcast DHCP probes, request or renew leases, release addresses, or write server configuration. Populate the source list from an authorised network registry/discovery result; an arbitrary DHCP offer does not automatically become trusted inventory.

The collector returns JSON with `schema_version: 1`, the exact configured `server_id`, `observed_at_unix_ms`, and a bounded `leases` array. Each lease includes `address`, `mac_address` and/or `client_id`, optional `hostname` and `lease_expires_at_unix_ms`, and an `options` array. An option has numeric `code`, `name`, JSON `value`, `observed_at_unix_ms`, and `source`: `dhcp_ack` for an option observed in the client's actual DHCP acknowledgement, `server_policy` for an option configured/offered by the server, or `client_request` for the client's parameter request list. The API exposes these separately as `received_options`, `advertised_options`, and `requested_options`; server policy is never represented as proof of receipt. A normal lease file often does not contain the full DHCPACK, so a collector must combine lease/server state with passive DHCPACK capture or equivalent server evidence to report all options received by a host.

Continuum correlates a lease only against registered `mac_addresses` or `dhcp_client_ids`. It never identifies a device from IP address or hostname alone. Results mark identity as `verified`, `unknown`, `conflict`, or `registry_stale`; stale observations are explicitly marked and conflicting/unregistered clients remain unresolved. DHCP data is observational evidence only and does not authorize a restart or network change.

The authenticated API and CLI surfaces are:

- `GET /devices/inventory` / `nmc device inventory`
- `GET /devices/dhcp` / `nmc device dhcp`
- `GET /devices/home-assistant` / `nmc device home-assistant`
- `GET /devices/home-assistant/reconciliation` / `nmc device home-assistant-reconcile`
- `GET /devices/controllers/diagnostics?controller_id=<id>` / `nmc device diagnostics --controller-id <id>`
- `POST /devices/controllers/actions` / `nmc device action --request-json '<json>'`

The authenticated Control Room at `/services/health/monitoring` also presents the inventory as a searchable table and an interactive grouped graph. Graph edges are limited to verified controller-to-host management links and declared dependencies that resolve to another registered device; they do not represent physical switch cabling. Device status and inventory revision/freshness remain visible. Tracey health enriches the matching registered device row and graph node only when its reported host/address resolves to exactly one registered identity; it never creates a second host node. Ambiguous or unmatched agents remain once in an explicit unlinked-evidence list. Device drilldown reuses the existing Tracey agent view and control gates, filters read-only DHCP collector results to the device's registered MAC/client IDs, shows exact-ID Home Assistant reconciliation on request, and can run read-only controller diagnostics. It never sends a controller mutation: the UI does not have a server-validated dependency/monitoring preflight API and must not manufacture the action assertions required by `POST /devices/controllers/actions`. The inventory, Tracey, Home Assistant, DHCP and diagnostic requests continue to use the authenticated route guard and their service-specific access levels.

For Kubernetes workload recovery, `nmc k8s recovery-status --cluster-id <id> --namespace <name> --deployment <name>` reports the active context, live host placement and structured blockers. `nmc k8s restart-deployment` requires the same scope plus an operator-stable `--request-id`; it performs a fresh read-only preflight first, then submits exactly one guarded request. Continuum repeats the preflight and compares the Deployment resource version immediately before applying the restart, so the CLI check is informative and never substitutes for the server-side safety gate.

Redfish diagnostics follow the service root's Systems and Managers links. They report the configured vendor profile and vendor family detected from the service root/system/manager identity fields, system manufacturer/model/power/health, advertised reset types, and BMC manager manufacturer/model/type/firmware/health. HP iLO, Dell iDRAC, and AMI MegaRAC models can expose different System and Manager IDs; Continuum follows validated local Redfish links instead of assuming their paths. Missing optional Manager data is reported as unavailable, while missing or unsafe Systems links fail closed. This provides standard Redfish interoperability, not a claim that physical devices from each vendor have been validated.

Inventory and diagnostics require Continuum `observe`; power actions require Continuum `control`. Power actions are unavailable unless both `NMC_DEVICE_POWER_CONTROL_ENABLED=true` and the selected controller's `power_actions_enabled` setting are true. An action also requires a fresh inventory, exact inventory and dependency-graph revisions, matching controller/device identity, current power-state evidence, the exact configured affected-service and dependency sets, healthy prerequisite/dependent/monitoring assertions, a change ID and reason. The action request ID is idempotent: Continuum writes a durable intent before contacting hardware and records the result; an intent without a final record blocks a repeat until an operator checks the controller.

Set `NMC_DEVICE_ACTION_AUDIT_PATH` to an owner-only regular file on protected persistent storage. Continuum holds an exclusive audit lock across request de-duplication and the controller operation, fails closed if audit history is malformed or incomplete, and requires each intent/outcome record to reach storage before proceeding. Redfish actions require the BMC to advertise the exact action target and requested reset type; IPMI starts only from fixed system paths with a minimal child environment; Turing Pi actions require an explicit success acknowledgement. Each hardware call has a bounded timeout, and the controller's resulting power state is checked. Conductor remains responsible for obtaining and verifying live Prometheus/Grafana, service, dependency and host evidence before submitting an action, then checking affected service health after the restart. Keep the global feature flag off until mock protocol tests, audit persistence, staging deployment and a supervised non-production action have all passed.

Current limitations are tracked in `docs/functional_tests_and_validation.md` §0.5n: live hardware diagnostics and supervised action validation remain required for HP iLO, Dell iDRAC, and MegaRAC. An on-host DHCP collector adapter and the passive ACK capture/export needed for complete received-option evidence do not yet exist. Automatically importing the SwarmHPC registry, mock IPMI/Turing Pi protocol tests, staged deployment, and end-to-end post-action service verification remain required before enabling power control in production.
